# 데이터 이동 및 운영

## 전체 ZIP 형식 v1

```text
manifest.json
RESTORE.md
notes/<note UUID>.md
attachments/<note UUID>/<attachment UUID>.png  # 또는 jpg/gif/webp/bin
```

Markdown 파일명은 제목과 관계없이 UUID로 유일합니다. 파일 본문은 UTF-8이며 첨부 이미지는 `![원래 이름](../attachments/<note UUID>/<attachment UUID>.png)`처럼 상대 경로를 씁니다. JSON에는 형식 이름 `hanjul-notes`, `format_version: 1`, 내보낸 시각과 각 메모의 ID·선택적 제목·원본 작성/수정 시각·태그·중요/보관/삭제 상태·수정 버전·Markdown 경로가 있습니다. 첨부 정보는 원래 이름, MIME, 크기, 소유 메모 ID, 생성 시각, ZIP 경로와 SHA-256을 보존합니다. 본문의 원본은 `.md` 파일 한 곳입니다.

**웹 UI → 설정 → 전체 ZIP 내보내기.** 서버는 하나의 읽기 트랜잭션에서 메모와 첨부의 일관된 스냅샷을 읽습니다. 임시 ZIP은 메모리 8MB 이후 디스크로 전환합니다. 비밀번호·세션·API 토큰·패스키는 내보내기에 포함하지 않습니다.

**설정 → ZIP 가져오기 → 추가·건너뛰기·첨부 개수 검토 → 확인하고 가져오기.** 미리보기는 메모를 변경하지 않으며 검증된 ZIP을 서버 DB에 30분간 준비합니다. 확인 시 재검증합니다. 기존 ID는 내용이 달라도 건너뜁니다. 기존 메모를 덮어쓰는 가져오기는 제공하지 않습니다. 실행 사이에 ID가 추가돼도 같은 규칙을 다시 적용합니다. 메모와 첨부 전부를 한 DB 트랜잭션으로 가져옵니다. 오류 시 전부 취소합니다.

악성 경로, 중복 경로/ID, 잘못된 관계, 크기 초과, 첨부 체크섬 불일치, 지원하지 않는 형식을 거부합니다. ZIP을 파일시스템에 그대로 압축 해제하지 않습니다. 지원 형식은 이 앱의 v1 ZIP이며 네이버 원본 형식은 추측하지 않습니다. 후속 어댑터는 출처를 파싱해 `validate_note`가 받는 공통 모델로 변환하고 같은 미리보기/트랜잭션 규칙을 재사용하는 방향으로 추가할 수 있습니다.

## 운영 백업

메모와 첨부파일 바이트는 같은 SQLite DB에 있으므로 별도의 업로드 폴더를 복사할 필요가 없습니다. DB 파일의 단순 복사 대신 SQLite Online Backup API를 이용합니다. 실행 중인 WAL 파일까지 반영한 일관된 백업입니다.

프로젝트 디렉터리에서:

```sh
.venv/bin/python scripts/backup.py
# 또는
.venv/bin/python scripts/backup.py --data-dir .data --output backups/manual.sqlite3
```

기존 백업은 덮어쓰지 않습니다. 파일 권한 600, 무결성 검사 및 메모/첨부 개수 확인을 수행합니다. 이 백업에는 **비밀번호 해시, API 토큰 해시, 패스키 공개 키 및 설정**도 포함되므로 비공개로 취급하세요. 원본 비밀번호와 토큰 문자열은 저장하지 않습니다. 실행 중 단순히 `memo.sqlite3`만 복사하거나 SQLite 파일을 네트워크 공유 폴더/클라우드 동기화 드라이브에 두지 마세요.

운영자는 매일 `backup.py` 실행을 OS 스케줄러에 등록하고, 일별 7개·주별 4개·월별 6개처럼 보존 정책을 적용할 수 있습니다. 이 프로젝트는 시스템 스케줄러를 임의로 설치하지 않습니다. 생성한 백업을 서버 밖 암호화된 저장소에도 복사하고 최소 월 1회 새 폴더에 실제 복원해 확인하세요. 같은 디스크의 백업만으로는 디스크 고장에 대비할 수 없습니다.

## 복원

기존 서버를 종료하고 새 빈 디렉터리로 복원합니다. 기존 데이터에 덮어쓰지 않습니다.

```sh
.venv/bin/python scripts/restore.py backups/manual.sqlite3 --to .data-restored
MEMO_DATA_DIR=.data-restored .venv/bin/python app.py
```

복원된 DB의 기존 비밀번호로 로그인합니다. 복원은 웹 세션·진행 중인 인증 요청·임시 가져오기를 지우고 메모·첨부·API 토큰·비밀번호·패스키·저장소 식별자는 보존합니다. 새 폴더에 `initial-password.txt`가 생기지 않는 것이 정상입니다. 의심스러운 유출 이후 복원이라면 비밀번호를 바꾸고 외부 API 토큰을 각각 폐기하세요. 기존 데이터 디렉터리는 검증이 끝날 때까지 보관합니다.

백업 검증 명령: `.venv/bin/python scripts/verify_restore.py backups/manual.sqlite3`. 임시 폴더에 복원하고 메모·첨부·인증 설정이 원본과 일치하는지 확인한 뒤 임시 폴더를 지웁니다. 실사용 DB를 건드리지 않습니다.

## 배포

특정 호스팅 계정 없이 실행할 수 있습니다. [설치 안내](SELF-HOSTING.md)는 로컬·NAS·AWS·일반 서버 구성을 제공합니다. 기본 바인딩 `127.0.0.1:8787`은 외부에 노출되지 않습니다. 휴대폰에서 접속하려면 사용자 소유 서버 또는 PC로 접근 가능한 네트워크와 아래 구성이 필요합니다.

1. Python 3.11+ / SQLite FTS5 trigram이 있는 단일 Linux VM 또는 자체 서버에 소스를 설치합니다.
2. 전용 OS 사용자와 영속 로컬 디스크의 데이터 폴더(예: `/var/lib/hanjul`)를 만들고 해당 사용자만 접근하도록 권한 700을 설정합니다. 앱 코드와 데이터 볼륨을 분리합니다.
3. `MEMO_DATA_DIR=/var/lib/hanjul`, `MEMO_HOST=127.0.0.1`, `PORT=8787`, `MEMO_PUBLIC_ORIGIN=https://메모앱의-실제-도메인`, `MEMO_SECURE_COOKIE=1`로 Waitress를 실행하고 systemd 등으로 재시작을 관리합니다.
4. Caddy 또는 Nginx 같은 역방향 프록시에서 HTTPS를 종료하고 동일 출처의 요청을 전달합니다. **원래 Host 헤더를 보존**하세요. 프록시 공개 주소와 요청 Origin이 다르면 CSRF 검사가 거부합니다. 정적 파일과 API는 같은 origin을 사용하며 CORS를 열지 않습니다.
5. 프록시 업로드 크기 한도를 앱의 256MB 이상(또는 운영상 더 작은 한도)으로 맞추고 업로드/내보내기 타임아웃과 디스크 여유를 확인합니다. 대용량 ZIP은 시간과 임시 디스크가 필요합니다.
6. DB·첨부 영속 볼륨을 포함하는 백업 작업과 실제 복원 훈련을 구성합니다. 재시작·새 버전 배포 후 메모와 첨부를 읽어 확인합니다.

서버리스 임시 파일시스템이나 매 배포 초기화되는 디스크에 DB를 두면 데이터가 사라집니다. SQLite 파일을 여러 서버에 공유하는 수평 확장은 지원하지 않습니다. 한 앱 프로세스의 Waitress 4개 스레드를 기본으로 사용합니다. 로그인 실패 제한은 IP별 5분/10회, 프로세스 메모리 기반이므로 재시작 시 초기화됩니다. 공개 서비스에는 프록시의 추가 요청 제한이 적합합니다.

의존성은 `requirements.lock.txt`의 정확한 버전을 사용하세요. 서버 로그에 메모 본문·비밀번호·토큰을 직접 출력하지 않습니다. 기본 HTTP 접근 로그에 URL 쿼리(검색어)가 남을 수 있으므로 운영 프록시 로그에서 검색 문자열을 제외하거나 로그 접근·보존을 제한하세요.

환경변수 목록은 `.env.example`을 참조하세요. `.env` 파일은 자동 로드되지 않으며 실행 환경에 직접 설정합니다. API 토큰을 프런트엔드 빌드 변수나 소스 저장소에 넣지 않습니다.


## 로그인과 패스키 운영

패스키는 WebAuthn 표준과 `webauthn` 서버 검증 라이브러리를 사용합니다. 사용자 확인(UV)을 필수로 요구하며 서명, 일회용 challenge, RP ID, 정확한 origin과 사용자 식별자를 검증합니다. challenge는 5분 유효하고 시작한 세션/브라우저에 연결하며 검증 시 소비합니다. 기기가 지문·얼굴·PIN 중 무엇을 사용했는지는 앱이 구분하지 않습니다. 서버에는 공개 키와 인증 메타데이터만 저장합니다.

`MEMO_PUBLIC_ORIGIN`은 경로 없는 고정 HTTPS 주소입니다. 로컬 개발만 `http://localhost:8787`을 허용합니다. 포트를 바꾸면 이 변수도 실제 주소에 맞추세요. HTTPS origin은 자동으로 Secure 쿠키를 사용합니다. 프록시는 Host를 보존하고 정적 페이지/API를 같은 주소로 제공해야 합니다. 휴대폰에서 localhost는 휴대폰 자신을 가리키므로 원격 PC 앱에 접속하는 주소로 사용할 수 없습니다.

패스키의 RP ID는 origin의 호스트명입니다. 다른 도메인으로 이전하면 새 도메인에서 비밀번호로 로그인한 뒤 패스키를 다시 등록하세요. 별도 시험 사이트의 등록은 본 앱으로 복사하지 않습니다. 원래 도메인으로 DB를 복원하고 기기에도 패스키가 남아 있다면 복원된 공개 키로 인증할 수 있습니다. 패스키가 동기화되는지는 기기의 자격 증명 제공자 설정에 따릅니다.

로그인 유지 시 HttpOnly/SameSite=Strict 쿠키와 서버 세션에 30일 절대 만료를 적용합니다. 해제하면 브라우저 세션 쿠키와 서버 최대 12시간을 적용합니다. 브라우저의 세션 복원 기능 때문에 창을 닫는 것만으로 로그아웃을 보장하지 않으므로 공유 기기에서는 명시적으로 로그아웃하세요. 최근 5분 본인 확인은 민감한 설정과 ZIP 입출력에 적용하며, 재인증 시 세션 쿠키를 교체하고 원래 만료일을 유지합니다.

분실 기기는 설정에서 해당 패스키를 삭제하고 로그인된 브라우저도 확인·해제하세요. 패스키 삭제는 그 키로 로그인한 세션을 모두 해제하지만 비밀번호로 로그인한 세션까지 해제하지는 않습니다. 비밀번호 변경/운영자 재설정은 모든 웹 세션과 진행 중인 인증을 해제하며, 패스키와 API 토큰은 유지하므로 유출 사고 시 각각 명시적으로 폐기하세요. 서버의 패스키 삭제는 기기 비밀번호 관리자의 항목을 지우지는 않습니다.

인증 테이블 마이그레이션은 앱 시작 시 추가 방식으로 수행됩니다. 기존 세션의 원래 만료일과 메모·첨부는 보존하며 기존 세션의 민감한 작업은 재인증을 요구합니다. 업데이트 전 DB 백업을 만들고 롤백은 서버를 멈춘 뒤 검증한 백업을 새 폴더에 복원하는 방법을 사용하세요.
